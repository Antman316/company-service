## Request flow

`fetch` → `seedRegistry` (idempotent company/coverage seed) → `/api/*` →
session lookup → JSON router → domain handlers. Non-`/api` → SPA.

<a name="static-serving"></a>
### Static serving

Two modes, ASSETS binding preferred:

1. `env.ASSETS` set → request proxied to the binding (normal `wrangler deploy`
   with `assets` config).
2. Otherwise → serve from `src/static.ts`, generated by
   `scripts/gen-static.mjs` from `web/dist` (used in the V1 deploy because the
   deploy credential cannot call the assets-upload API; ~280 KB inlined,
   ~480 KB bundle total).

SPA fallback: unmatched non-`/api` paths return `/index.html` (client routing).

## Agent run loop (`advanceCase`)

Triggered by events — case creation approval, mandate activation, inbound
merchant message, `/run`, follow-up sweep, approve/reject — never a
continuously running loop:

1. Load case; bail if paused/terminal/revoked-mandate.
2. Coverage gate (`checkCoverage`) — uncovered → `UNSUPPORTED` + manual_handoff.
3. Build/reuse `CasePlan` steps from the provider (`TASK:plan`).
4. For each pending action: **policy classification first** —
   AUTO_ALLOWED → execute via `ToolRouter`; USER_APPROVAL_REQUIRED → create
   `approval_requests` row, stop; PROHIBITED/UNSUPPORTED → record + stop.
5. Adapter `execute` → external message → store in `external_messages`,
   evidence row, cost event.
6. Interpret reply (`TASK:interpret`) → outcome update → schedule follow-ups
   (`within N days` → `check_commitment` at now+N) → state transition.
7. `ctx.waitUntil` is not used for durability — D1 is the source of truth and
   the cron sweep re-drives anything due, so restarts are irrelevant.

## Durable execution

`scheduled()` (cron `*/5 * * * *`) selects pending `follow_ups` with
`due_at <= now` for non-paused, non-terminal cases with active mandates, marks
them `fired`, and calls `advanceCase(caseId, "follow_up")`. The follow-up
engine re-checks whether the merchant's commitment was fulfilled — e.g.
outcome PROMISED with elapsed deadline → sends a bounded follow-up message
(grant `follow_up` required) or escalates to WAITING_FOR_CUSTOMER if the
mandate doesn't cover it.

Scenario D is covered by design + test: all state lives in D1; a "restart" is
just the next invocation.

## Tool router

`routeAction` normalizes plan actions to adapter calls: `send_message`,
`check_status`, `accept_offer` (always gated), `upload_evidence`,
`request_escalation`. Unknown kinds → `UNSUPPORTED` result, never guessed.

## Model routing

`providers/registry.ts` resolves the provider per task: customer's connected
provider for the tenant → `local_dev` fallback. Requests carry a `task`
(`classify|extract|plan|compose|interpret|vision`) so a future router can map
tasks to model tiers; V1 keeps one provider per connection and records
`provider`/`model` on every `case_actions`/`cost_events` row.

## Cost accounting

`cost_events` rows per case: kind (`model_call`, `email_send`,
`browser_minutes`, …), provider, model, tokens in/out when reported,
`micro_usd`. `/api/economics` aggregates per-case cost, provider breakdown,
approval/follow-up counts — the internal economics view (currently all
`local_dev` rows at $0; real pricing lands with real providers).
